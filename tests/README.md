# Проверки SQL

Из корня проекта:

```sh
npm ci
npm run test:sql
```

Используется Node.js test runner и зафиксированная dev-зависимость PGlite. Каждый запуск выполняет настоящую схему `supabase/schema.sql` в изолированной PostgreSQL в памяти. Схема Auth, JWT-контекст, роли API и их исходные grants воспроизводятся только в тестовой среде. `.env`, рабочие ключи и подключение к Supabase для запуска не нужны.

`internal-rpc-access.test.mjs` проверяет запрет прямого вызова внутренних функций, сохранение разрешённых серверных вызовов и применение миграции к состоянию с прежними открытыми правами. Регрессии проверяются на уровне выполнения SQL, а не поиском строки `REVOKE` в файле.

Дополнительные наборы шага 1б:

- `external-rpc-roles.test.mjs`: создание/регистрация, роли, управление администраторами, пары, таблицы мест.
- `external-rpc-brackets.test.mjs`: генерация/перегенерация, раскладка сетки, принадлежность UUID, прямые клиентские записи и совместимость с текущим UI.
- `external-rpc-scoring.test.mjs`: ручные и live-RPC по матрице шести ролей; невозможность изменять чужой турнир через связи матчей, включая старые некорректные связи.
- `external-rpc-migration.test.mjs`: двукратное применение исторического патча шага 1б, отзыв старых табличных/поколоночных grants, сохранение результатов и повторяемость определений этого патча. Последующие миграции проверяются отдельно.

Для проверки всей внешней матрицы на сохранённой **старой текущей схеме** и точечной миграции можно задать `TENIS_TEST_SCHEMA_PATH` и `TENIS_TEST_MIGRATION_PATH` перед `node --test tests/external-rpc-*.test.mjs`. Это тестовые пути; рабочая БД не используется.

Эти тесты не проверяют настоящий вход OAuth, PostgREST/GraphQL, доставку Realtime или конкуренцию нескольких соединений. Для них требуется отдельная интеграционная среда. Тесты доступа также не означают, что уже исправлены известные проблемы спортивных правил: они перечислены в `../STABILIZATION_PLAN_2026-09-05.md`.


Шаг 2:

- `participant-privacy.test.mjs` проверяет статусы заявок и состав, все пути прямого чтения контакта, сохранение регистрации/пар, собственные/чужие/объединённые профили, разрешённые поля записи и повторную миграцию без потери данных.
- `auth-player-context.test.mjs` выполняет настоящий Pinia store с подставленным API без сети: очистка при смене аккаунта/выходе, запоздавший ответ предыдущего пользователя, повтор запроса после ошибки.
- `supabase/checks/participant_privacy.sql` содержит проверки фактических grants и политик для рабочей БД.

`manual/participant-privacy-api.mjs` — **ручная сетевая интеграционная проверка**, не входит в обычный запуск тестов. Берёт только публичные Vite-настройки Supabase. Требует `PRIVACY_SMOKE_TOURNAMENT` с UUID специального турнира `privacy-smoke-20260905`; чтение проверяет отказ контактов/профилей и безопасные вложенные имена. Флаг `--register-and-observe` создаёт вымышленную pending-заявку и ожидает до 3 минут одобрения через UI; затем проверяет публичное чтение и отсутствие контакта в событии Realtime. Этот режим меняет только тестовые данные и не предназначен для обычного турнира. После завершения тестовый турнир оставлен закрытым; для повторной регистрации его нужно намеренно открыть в выделенном тестовом сценарии.

Шаг 3:

- `knockout-byes.test.mjs`: single elimination для каждого размера 2–64, настоящий путь группы → плей-офф для каждого числа квалификантов 2–64, равномерные BYE, ручной порядок без потери/дублирования участников, произвольный порядок завершения матчей и один чемпион за N−1 сыгранных матчей.
- Дополнительно: шесть квалификантов из трёх групп с сохранением групповых сетов при перегенерации, коррекция результата в сетке с BYE, все поддерживаемые размеры double elimination, включая двоих. Сохраняется существующая модель одного гранд-финала без reset-матча.
- Все неподдерживаемые размеры double elimination в диапазоне 3–63 проверяются через generate/rebuild. Временные тестовые BEFORE DELETE-триггеры доказывают отказ до попытки удалить матчи/сеты; снимки проверяют сохранность данных и версий сетки.
- Миграция применяется дважды: определения совпадают с канонической схемой, владельцы/ACL и существующие результаты сохраняются. `supabase/checks/knockout_byes.sql` проверяет три определения/права и выявляет старые полностью пустые матчи первого раунда.
- Для отдельной проверки обновления сохранённой схемы перед шагом 3: задать `TENIS_TEST_SCHEMA_PATH` и `TENIS_TEST_MIGRATION_PATH=supabase/upgrades/20260905205404_fix_knockout_byes.sql`, затем запустить `node --test tests/knockout-byes.test.mjs`.

Допустимые состояния сетов 0–7 перечисляются независимым обходом возможных игровых переходов для тенниса/падела; проверяются все допустимые последовательности побед в сетах для best-of-3/5, промежуточные сеты, индексы, типы/диапазоны JSON и точное определение победителя.

## Шаг 5: приоритет LIVE

Актуальный полный набор — **117 тестов**, включая 16 в `live-priority.test.mjs`.
Они проверяют обязательные версии, финальный ручной результат, исключение ручного
ввода при активном live, права прекращения, явное продолжение, защиту обеих веток
и согласованность результата/standings. Отдельно проверен повторяемый пересчёт
старых агрегатов без изменения очков или победителей.

Регрессии прошлых этапов приведены к новому контракту: пустые и промежуточные
ручные результаты теперь отклоняются, прежний прямой reset закрыт. Состояния
незавершённого live для тестов правил задаёт явно привилегированный helper
`seedPartialScore`; это подготовка fixture, не клиентский путь сохранения.

Проверка обновления (путь к сохранённой схеме подставляется из своей среды):

```sh
TENIS_TEST_SCHEMA_PATH=/path/to/schema-before-step5.sql \
TENIS_TEST_MIGRATION_PATH=supabase/upgrades/20260906114558_prioritize_live_scoring.sql \
node --test tests/live-priority.test.mjs
```

Harness применяет миграцию дважды. PGlite не заменяет проверку разных соединений:
реальное ожидание блокировки в PostgreSQL TENIS проверено через MCP + браузер,
описание — `supabase/checks/live_priority_concurrency.md`. Все такие записи
ограничены двумя закрытыми тестовыми турнирами.

## Шаг 10: воспроизводимый выпуск

На завершении шага 10 набор содержал **172 теста**; после шага 11 — **189**.
Запускать на Node из `.nvmrc`.
`npm run test:sql` ограничивает параллелизм двумя процессами для CI.

```sh
npm ci
npm run test:sql
TENIS_TEST_INSTALL_MODE=fresh npm run test:sql
TENIS_TEST_INSTALL_MODE=upgrade npm run test:sql
```

Каждый режим прошёл **172/172** в чистой копии без `.env` и прежнего node_modules
на Node 24.20.0. Исходные 11 патчей перенесены в `supabase/upgrades/` без изменения
SQL. Прежние примеры `TENIS_TEST_MIGRATION_PATH` используют новый путь.

- `database-release.test.mjs`: три проверки SHA-256/порядка файлов, совпадения
  каталогов schema/fresh/upgrade (включая ACL/RLS/триггеры/публикацию) и отказа
  baseline поверх существующей текущей или исторической модели.
- `build-env.test.mjs`: сборка отказывает при приватной переменной с публичным
  `VITE_`-префиксом, не печатая её значение.
- `scripts/check-postgres.mjs`: настоящий PostgreSQL 17, заполненная старая
  схема → вся цепочка, сравнение каждого исходного значения, pg_dump/pg_restore,
  восстановленные права/публичное чтение/LIVE. Запуск `npm run test:postgres`
  требует PGHOST=127.0.0.1, PGPORT, PGUSER и PGPASSWORD отдельного тестового
  сервера. Сеть к рабочему Supabase не используется, тестовые БД удаляются.
- `TENIS_TEST_CLI=1` дополнительно применяет baseline через CLI и проверяет
  пропуск при повторном запуске. `TENIS_PG_CONTAINER` позволяет выполнять
  PostgreSQL-команды внутри локального контейнера, как в GitHub Actions.
- После обновления зависимостей повторены **59/59** браузерных проверок на
  новом Vite-процессе. Сценарий берёт origin открытой локальной страницы,
  поэтому поддерживает отдельный тестовый порт.

Проверка Docker/PostgreSQL с shim не заменяет hosted Auth, Google OAuth, PITR
или физический телефон. Workflow проверен actionlint 1.7.12; первые реальные
GitHub jobs появятся после публикации репозитория. Порядок выпуска и принятия
baseline существующим проектом — `../docs/RELEASE.md`.
