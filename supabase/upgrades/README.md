# SQL-обновления и исторические миграции

Это исторический протокол шагов 1–8; числа тестов относятся к моменту выпуска.
Актуальная установка, цепочка обновления и восстановление описаны в
[руководстве выпуска](../../docs/RELEASE.md). SQL из этой папки применяется
только явно, в порядке `../database-release.json`. `pre-stabilization.sql` —
исходник ревизии 2863c88 для тестов, не выполнять его в существующей БД.

## Шаг 1а: внутренние функции

`20260905194009_restrict_internal_rpc_execution.sql` закрывает прямой вызов пяти внутренних функций сетки для `PUBLIC`, `anon`, `authenticated`. Таблицы, результаты и разрешённые внешние RPC не изменяются. Повторное применение безопасно; пять отзывов прав выполняются в одной транзакции.

Перед применением:

1. Убедиться, что целевая БД использует текущую multi-sport модель, и выполнить `../checks/internal_rpc_access.sql`. Сигнатуры должны существовать; разрешённые внешние RPC и helpers должны иметь общего привилегированного владельца. На TENIS это проверено read-only: `postgres`.
2. Запустить `npm run test:sql` и `npm run build` из корня проекта. Тесты используют изолированную БД в памяти, без подключения к Supabase.
3. Применить **только этот файл** к выбранной среде как владелец функций, например через SQL Editor. Для MCP использовать операцию применения миграции с именем `restrict_internal_rpc_execution` и точным содержимым файла.
4. Повторить `../checks/internal_rpc_access.sql`: для каждой внутренней функции `anon_execute`, `authenticated_execute`, `public_execute` должны быть `false`; все сигнатуры присутствуют. Внешние RPC сохраняют права выполнения.
5. На тестовом турнире проверить генерацию сетки/групп и сохранение результата через обычный интерфейс организатора. Изолированные SQL-тесты не заменяют проверку API рабочей среды.

После выпуска записать среду, применённую миграцию и результат проверки в `../../STABILIZATION_PLAN_2026-09-05.md`. Возврат прежних клиентских grants снова открывает найденную уязвимость; при ошибке разрешённых операций исправить владельца/права вложенного серверного вызова.

## Шаг 3: сетки и BYE

`20260905205404_fix_knockout_byes.sql` применяется после шагов 1а, 1б и 2. Заменяет три определения функций в одной транзакции, сохраняя владельцев и ACL; повторное применение допустимо.

- Оба генератора single elimination распределяют BYE по первому раунду без полностью пустых матчей. Непустые позиции сохраняют входной порядок участников. Исправление применяется также к плей-офф после групп.
- Для double elimination на двоих проигравший единственного матча верхней сетки попадает в слот B гранд-финала. Сохраняется существующая модель одного гранд-финала.
- Проверка неподдерживаемого размера double elimination остаётся до удаления матчей. Генерация для 3, 5, 6 и других неполных степеней двойки отклоняется с сохранением сетки/результатов.
- Миграция не перегенерирует существующие сетки. Полностью пустые ветви в старых турнирах, если они есть, требуют отдельного решения с учётом результатов.

Порядок для другой среды:

1. Убедиться, что предыдущие три патча применены, функции принадлежат `postgres`, а все шесть helpers закрыты. Проверить старые пустые ветви вторым запросом `../checks/knockout_byes.sql`.
2. Выполнить `npm run test:sql` и `npm run build`. При обновлении проверить также сохранённую исходную схему плюс точечный патч через тестовые переменные из `../../tests/README.md`.
3. Применить только этот файл через MCP `apply_migration` с именем `fix_knockout_byes` либо SQL Editor.
4. Повторить `../checks/knockout_byes.sql`: три строки `passed=true`. Повторить `../checks/internal_rpc_access.sql`: helpers закрыты, внешние RPC доступны; сверить число строк и контрольные суммы данных до/после.

## Шаг 4: контракт результата

`20260905211522_validate_match_set_results.sql` применяется после шага 3. Обновляет четыре функции в одной транзакции с сохранением владельцев/ACL; повторное применение допустимо, существующие результаты не пересчитываются.

- `update_match_sets`: массив объектов с числовыми целыми `set_index`, `side_a_games`, `side_b_games`. Индексы уникальны и непрерывны от 1, максимум 3/5 по формату. Порядок объектов в массиве не важен — хронология определяется индексами. SQL/JSON null, пропущенные поля и числовые строки отклоняются; `[]` остаётся явным сбросом результата.
- Завершённые сеты: 6:0–4, 7:5, 7:6 и обратные счета. Допустимый промежуточный сет может быть только последним; он сохраняется, но не увеличивает число выигранных сетов и не присуждает победу. После двух/трёх выигранных сетов дополнительный сет запрещён, даже 0:0.
- `tiebreak_to=10` задаёт очки обычного тайбрейка; результат сета всё равно 7:6. Match-tiebreak вместо решающего сета и advantage-set не добавляются.
- Весь массив проверяется до DELETE/INSERT/UPDATE. Ошибки набора сетов возвращают SQLSTATE `22023`; прежние результаты и зависимые матчи сохраняются.
- `update_football_result` принимает только футбол; `update_match_sets`, `start_live_match`, `record_point` — только теннис/падел. Проверка record_point действует и для ранее созданной футбольной live-сессии, включая undo. Права owner/editor/counter сохраняются.

3. Применить только этот файл через MCP `apply_migration` с именем `validate_match_set_results` либо SQL Editor.

В TENIS применено через MCP: серверная версия **20260905212151**, локальный файл **20260905211522**. Определения функций и права проверены; данные 11 таблиц до/после совпали. вид результата и очки тай-брейка в match_sets, снимает предел 7 геймов для
длинных сетов, вводит проверку правил и обновляет ручные/live-RPC.

1. Выполнить `npm run test:sql`, `npm run build` и проверку обновления старой
   схемы по `../../tests/README.md`.
2. Применить этот SQL-файл через MCP `apply_migration` с именем
   `add_itf_2026_scoring`, затем `20260906073551_lock_started_tournament_sport.sql`
   с именем `lock_started_tournament_sport`. Второй патч закрывает обход блокировки
   через смену вида спорта. Изменений существующих турниров/результатов нет.
3. Выполнить три read-only запроса `../checks/itf_2026_scoring.sql`:
   12 passed=true, восемь helpers закрыты, нет неверных последовательностей.
   Этот файл заменяет проверку текущих определений из `match_set_results.sql`,
   которая описывает историческое состояние шага 4.
4. Проверить сохранность данных и Security Advisor; проверить UI на вымышленных
   участниках, включая обычный и матч-тай-брейк, No-Ad, ошибочный счёт и reload.

Применено в TENIS 6 сентября 2026: серверные версии **20260906071725** и
**20260906073711**. Повторно применять следует оба патча в том же порядке.
Клиент требует эти колонки и функции; сначала применяется SQL, затем публикуется
фронтенд. В этой итерации UI проверен в локальном приложении, внешний хостинг
не публиковался. Не применять исторические миграции поверх этого расширения.
