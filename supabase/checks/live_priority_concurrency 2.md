# Шаг 5: проверка одновременных запросов, 06.09.2026

Основной контракт проверяется в `tests/live-priority.test.mjs`. PGlite выполняет
запросы последовательно и сам по себе не доказывает межтранзакционную блокировку.
Поэтому дополнительно использованы две независимые сессии PostgreSQL TENIS:
запрос через MCP и запрос реального браузера через Supabase Data API.

Все записи выполнялись на закрытых синтетических турнирах:
- `800da77a-fef9-46eb-a9ef-05afbe42fe29`, «ТЕСТ — приоритет LIVE 06.09.2026»;
- `bef9d49a-8299-4148-a252-798791d52fdb`, «ТЕСТ — одновременный счёт 06.09.2026».

## Ручной результат

Матч `41d310e3-9fca-4d63-96a0-ad5e7d828181`, исходная версия 2.
В браузере подготовлены 6:4, 6:4. В отдельной транзакции вызван разрешённый
`update_match_sets` с 6:0, 6:0 и версией 2; перед COMMIT транзакция удерживалась
через `pg_sleep(10)`. В это время нажата кнопка сохранения в браузере.

Перед COMMIT запрос `pg_locks` показал **1** ожидающую блокировку transactionid
именно текущей транзакции. После COMMIT браузер получил конфликт. В базе остались
6:0, 6:0, победитель A и итог 2:0; в форме сохранился черновик 6:4, 6:4.
Загрузка актуального результата после явного подтверждения показала 6:0, 6:0.

## Очки live и очередь

Матч `dcac1025-da41-4edd-837a-bb62eea89c15`, исходная live-версия 0.
Отдельная транзакция записала одно очко A и удерживалась 10 секунд. В браузере
трижды быстро нажата сторона B. `pg_locks` снова подтвердил **1** ожидающую
транзакцию. Первое нажатие отклонено по версии, оставшаяся очередь отменена.
После обновления: **15:0**, live revision **1**, очков B нет.

Через UI проверены прекращение (revision 2, очки сохранены), продолжение
(revision 3, 15:0 сохранены), три быстрых корректных нажатия A (revision 6,
геймы 1:0), повторное прекращение (revision 7), отказ вручную завершить матч
с промежуточным 1:0 и сохранение окончательных 6:4, 6:4.

## Две вкладки и круговая форма

Матч `83a9b55f-99eb-4417-a6cd-b0a85405da08` открыт в двух вкладках. В первой
введены 6:4, 6:4, во второй сохранены 6:1, 6:1. Первая сохранила свой черновик
и показала конфликт; явная загрузка подтянула актуальные 6:1, 6:1.
Таблица результатов и standings обновились без перезагрузки страницы.

Попытки запускать только несколько MCP-вызовов через Promise.all не использованы
как доказательство параллельности: наблюдение перекрывающихся транзакций получено
именно в сценариях MCP + браузер выше.
