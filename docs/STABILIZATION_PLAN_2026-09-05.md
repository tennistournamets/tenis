# План стабилизации Tenis

Дата: 5 сентября 2026. Основание: `PROJECT_REVIEW_2026-09-05.md` и проверка текущего кода. Отчёт используется как перечень находок, которые нужно подтвердить, а не как инструкция автоматически выполнить все предложения.

Цель — сначала восстановить контроль доступа и корректность соревнований, затем надёжность ежедневной работы. Стек Vue/Supabase сохраняем. Старый `IMPLEMENTATION_PLAN.md` описывает другую, историческую модель организаций и не задаёт порядок этой работы.

## Как выполняем

Один шаг — отдельное законченное изменение: воспроизведение → исправление → проверка → запись результата здесь. Внутри крупного шага используем небольшие подпункты. Тесты добавляем вместе с исправлениями, а CI подключаем к уже работающим проверкам. Рефакторинг выполняем после защиты поведения тестами.

Различаем состояния: **очередь**, **в работе**, **проверено локально**, **применено и проверено в рабочей среде**. Локальная правка SQL сама по себе не исправляет рабочую БД. У каждого серверного шага должны быть изменение `schema.sql`, отдельный SQL для обновления существующей БД и проверка после применения.

## Существенные условия следующих шагов

- **Шаг 2:** простой запрет SELECT всей `entries` сломает текущие загрузчики. Закрытие контактов должно учитывать прямое добавление заявки администратором, `register_entry`, `form_random_pairs`, `form_manual_pairs`, `split_pairs`, вложенные `entry_members` и Realtime. Пользовательский store читает собственную запись `players`; удалять таблицу как неиспользуемую нельзя.
- **Шаг 4:** проверить 6:0–6:4, 7:5, 7:6; промежуточные 1:0 и 6:5; недопустимые 7:0 и 7:7; пропуски/дубли индексов, лишние сеты после победы, null/дробные/отрицательные значения, вызов sets-RPC для футбола. `tiebreak_to=10` сейчас задаёт очки обычного тайбрейка и не означает новый формат решающего match tiebreak.
- **Шаг 5:** одинаковый порядок блокировок у ручного и live-ввода; два редактора одновременно; конфликт revision; ручное завершение уже активной live-сессии. Одной проверки disabled-кнопок недостаточно.
- **Шаг 8:** проверить реальные сетевые события Supabase, включая удаление/пересоздание сетки и reconnect. Локальные имитации не заменяют эту проверку.
- **Шаг 10:** исторические миграции организаций вынесены в архив; baseline предназначен только для новой БД. Точечные обновления и принятие baseline существующим TENIS описаны в `docs/RELEASE.md`.

## Итерация 1б — применено и проверено в рабочей среде

Статус на 5 сентября 2026: **шаг 1б выполнен**. Следующим был шаг 2; его завершение описано ниже.

Подтверждённые проблемы и исправления:

- Прямые INSERT/UPDATE графа матчей позволяли организатору направить внутреннее продвижение результата в чужой турнир. Закрыта прямая запись структурных полей матчей; внутренние `propagate_winner`/`clear_downstream` дополнительно проверяют принадлежность следующего матча. Проверки покрывают и ранее сохранённые некорректные связи.
- `apply_bracket_layout` принимала чужие заявки. Добавлены проверки структуры пакета, уникальных ID матчей, принадлежности одобренных участников, отсутствия self-pair, уже введённых сетов и активного live. Пакет проверяется до первой записи. Один участник в разных раундах разрешён для совместимости с существующим редактором.
- Ручной порядок генерации молча отбрасывал неверные ID. Теперь чужие, null, повторные и неодобренные ID отклоняются; корректный порядок сохраняется, пропущенные участники дополняются. Сохранён контракт UI `manual + NULL` для начального заполнения.
- Пара из одной заявки дважды удаляла эту заявку. `form_manual_pairs` проверяет весь пакет до объединения: ровно два разных непарных участника doubles, одобрение, принадлежность турниру, отсутствие повторного использования. Некорректный пакет оставляет данные без изменений.
- `swap_bracket_slots` отклоняет NULL и неверные названия слотов; `get_standings` явно отклоняет чужую группу. `rebuild_bracket` проверяет права до создания снимка.
- Убраны прямые клиентские записи в группы, состав групп и live; запись остаётся через проверенные RPC. У `entries` разрешён UPDATE только статуса, у `matches` — только штатный сброс `winner_entry_id=NULL,status=ready` с RLS организатора. Сохранены используемые UI вставка участника/члена заявки, одобрение и удаление матчей/сетов.

## Шаг 5 — приоритет LIVE, завершение и версии

Статус: **применено и проверено в TENIS**, интерфейс проверен в локальном приложении.
По подтверждённому пользователем решению изменён прежний порядок ручного/live-ввода.
Промежуточные результаты остаются допустимыми состояниями live, но ручная форма
теперь принимает только окончательный результат матча.

Правила:

- Активный live блокирует ручное сохранение и поля обеих теннисных форм.
- «Сохранить результат и завершить матч» выполняет одну серверную транзакцию:
  проверка версии/прав/правил → результат → итог → победитель → продвижение.
  Пустой массив и незавершённый матч не очищают и не завершают результат.
- Организатор/редактор явно прекращает live с подтверждением. Очки, сеты и
  история сохраняются, победа не присуждается. Counter прекращать live не может.
- Продолжение возможно только явным действием. `record_point` больше не создаёт
  сессию и не возобновляет остановленную сессию автоматически.
- `matches.score_revision` хранится и изменяется сервером. Ручной теннисный/падел-
  и футбольный результат, а также начало/продолжение live проверяют ожидаемую
  версию матча. Очко/undo/прекращение проверяют обязательную live-версию.
  Новая версия появляется и при очке внутри гейма; старые формы/пакеты отклоняются.
- На конфликте очередь live-нажатий отменяется без автоматического повтора.
  Ручной черновик сохраняется; загрузка актуального результата заменяет его
  только после явного подтверждения. Кнопка сохранения устаревшего ввода отключена.
- Ручной окончательный результат после прекращения live закрывает сессию,
  заменяет её базу и очищает undo. Готовый результат нельзя отменить старым очком.
- Смена победителя запрещена, если любой зависимый матч по ветке победителя
  или проигравшего имеет результат/сеты/live. Исправление счёта с тем же победителем
  не затрагивает эти матчи. Полный откат зависимостей остаётся шагом 6.
- Прямой UPDATE статуса/победителя и DELETE отдельных сетов от клиента закрыты.
  Удаление всей сетки остаётся отдельной подтверждаемой операцией организатора.

Интерфейс получает матч, сеты и live согласованным снимком через

## Итерация 6 — безопасное исправление зависимых результатов

Статус: **применено и проверено в TENIS**, 6 сентября 2026. Локальная миграция
`20260906130008_safe_result_corrections.sql`, серверная версия **20260906132026**.
На завершении этой итерации следующим был **шаг 7** (теперь выполнен ниже).

Правила:

- Обычная поправка счёта с прежним победителем сохраняет зависимые матчи. В
  круговом турнире меняется таблица мест, остальные результаты остаются.
- При смене победителя и наличии зависимого счёта появляется список последствий:
  этап, раунд, номер матча, оба участника и действие. Подтверждение очищает счёт,
  сеты, пенальти и историю LIVE всех структурно зависимых матчей. Независимые
  матчи и места их участников сохраняются. Учитываются обе ветки double
  elimination и их общий гранд-финал без повторной обработки общего потомка.
- Групповой результат после создания плей-офф исправляется только с отдельным
  подтверждением пересоздания **всего плей-офф**, даже при прежнем победителе:
  могут измениться места и квалификация. Групповые результаты сохраняются;
  новые участники плей-офф берутся из обновлённой таблицы мест.
- Активный LIVE в исходном или любом затронутом матче блокирует коррекцию.
  Сначала организатор/editor явно прекращает подсчёт обычной командой LIVE.
- Превью не меняет данные. Подтверждение связано с исходной версией матча,
  точным отправляемым результатом и снимком зависимостей. Смена результата,
  состава, LIVE или структуры после просмотра требует нового подтверждения.
  При занятой строке запрос быстро отклоняется без автоматического повтора.
- Проверки и запись выполняются в одной транзакции. Внутренние функции записи
  закрыты от прямого API, новые RPC доступны только owner/editor своего турнира.
  Прежние RPC остаются совместимыми с клиентом шага 5 и блокируют опасную запись
  без подтверждения. Проверки ITF используются повторно, не копируются в новый
  клиентский алгоритм.
- После сброса LIVE остаётся пустая stopped-запись с увеличенной revision.
  Старые нажатия/stop/resume не могут стать действительными после нового старта.
  При пересоздании плей-офф новые UUID матчей также исключают старые запросы.
- Исправления доступны в активном турнире; статус завершённого турнира сам по
  себе не меняется. Сохраняется модель double elimination с одним гранд-финалом.

## Итерация 7 — сохранность несохранённого ввода
