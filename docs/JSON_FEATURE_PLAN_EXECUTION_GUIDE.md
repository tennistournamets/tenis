# Как другой AI должен читать и выполнять Bracketa Feature Plan

Эта инструкция относится к JSON-файлам с `document_type: "bracketa_feature_selection"`, созданным на странице разбора Score7. Пример: `/Users/dmitrijpanasiuk/Downloads/bracketa-feature-plan.json`.

JSON фиксирует продуктовый выбор пользователя. Это не готовое техническое задание и не безусловное разрешение менять код.

## 1. Главный контракт

AI должен соблюдать пять правил:

1. Реализовывать можно только элементы из `selected_changes`.
2. Элементы из `deferred_change_ids` находятся вне текущего объёма. Нельзя добавлять их «заодно».
3. Значения в `decisions` — принятые продуктовые решения, а не предложения.
4. Все `dependency_warnings` нужно разрешить до реализации затронутого пункта.
5. При `implementation_authorized: false` AI может изучать проект и готовить план, но не должен менять продуктовый код, схему БД или миграции. Начать реализацию можно после отдельного явного указания пользователя, например: «Утверждаю план. Реализуй этап A».

Если текст текущего сообщения пользователя явно разрешает реализацию, он имеет приоритет над сохранённым флагом. Простая передача JSON без такого указания означает запрос на анализ и план.

## 2. Значение полей JSON

| Поле | Как трактовать |
|---|---|
| `schema_version` | Версия формата. Для этой инструкции поддерживается версия `1`. Неизвестную версию нельзя интерпретировать по догадке. |
| `document_type` | Должно быть `bracketa_feature_selection`. Иное значение означает другой тип документа. |
| `source_review` | Источник продуктового анализа. Это контекст, а не техническая спецификация. |
| `generated_at` | Время сохранения. Используется для понимания актуальности, но не определяет приоритет. |
| `implementation_authorized` | Явный предохранитель от преждевременной реализации. |
| `instruction_for_codex` | Инструкция, с которой JSON был сформирован. |
| `selected_changes` | Главный список функций в объёме. Содержит смысл, фазу, решения и зависимости. |
| `selected_change_ids` | Контрольная копия идентификаторов. Должна совпадать с `selected_changes[].id`. |
| `deferred_change_ids` | Осознанно не выбранные функции. Их нельзя включать в оценку и реализацию текущего объёма. |
| `dependency_warnings` | Конфликты выбора. Пункт нельзя считать готовым к работе, пока конфликт не разрешён. |
| `user_notes` | Дополнительные ограничения пользователя. При конфликте с общим описанием они имеют приоритет. |

Поля внутри `selected_changes`:

- `id` — стабильный машинный идентификатор и основной ключ для зависимостей;
- `title` — понятное человеку название;
- `category` — область продукта: `registration`, `schedule` или `access`;
- `priority` — исходная рекомендация анализа (`high`, `medium`, `later`), но не статус выбора;
- `proposed_phase` — рекомендуемая последовательность;
- `decisions` — выбранное пользователем поведение;
- `dependencies` — функции, без которых пункт не должен планироваться как самостоятельный.

Важно: если функция присутствует в `selected_changes` с `priority: "later"`, пользователь всё равно её выбрал. Её нужно включить в общий roadmap на соответствующем позднем этапе. Значение `later` не переносит её обратно в `deferred_change_ids`.

## 3. Алгоритм чтения

Перед любыми изменениями AI должен выполнить эту последовательность.

### Шаг 1. Проверить структуру

- Проверить `schema_version` и `document_type`.
- Убедиться, что все `id` уникальны.
- Сравнить `selected_change_ids` с `selected_changes[].id`.
- Убедиться, что один идентификатор не находится одновременно в выбранных и отложенных.
- Проверить, что каждая зависимость ссылается на известный идентификатор.

При структурной ошибке AI должен назвать конкретные поля и остановить планирование затронутой части.

### Шаг 2. Построить граф зависимостей

- Узлы — выбранные изменения.
- Рёбра — значения `dependencies`.
- Выбранная зависимость задаёт порядок работ.
- Отложенная или отсутствующая зависимость блокирует только зависящий от неё пункт, а не весь план.
- Нельзя автоматически выбирать отсутствующую зависимость: это изменило бы решение пользователя.

### Шаг 3. Разделить выбор на состояния

Каждый пункт должен получить одно состояние:

- `ready` — выбран, зависимости выбраны, решений достаточно для планирования;
- `needs_product_decision` — выбран, но остаётся неоднозначное продуктовое правило;
- `blocked_by_dependency` — выбран, но необходимая функция отложена или отсутствует;
- `deferred` — явно не выбран.

### Шаг 4. Сверить с текущим продуктом

AI должен изучить фактический код и БД, потому что JSON описывает желаемое поведение, а не способ реализации. Минимально проверить:

- `README.md` и `docs/RELEASE.md`;
- актуальные инструкции репозитория (`AGENTS.md`, `CLAUDE.md`, если применимы);
- `src/views/PublicTournamentView.vue`;
- `src/components/RegistrationForm.vue`;
- `src/components/admin/TournamentSettingsForm.vue`;
- `src/views/AdminTournamentView.vue`;
- `src/lib/scoringAccess.js`;
- `supabase/schema.sql`;
- последнюю baseline и новые файлы в `supabase/migrations/`;
- `register_entry`, `update_tournament_settings`, публичный sync-state, RLS и роли;
- существующие SQL и UI-проверки.

Выводы только из frontend-кода недостаточны для функций лимита, дедлайна, доступа и конфликтов расписания. Их ограничения должны обеспечиваться сервером.

### Шаг 5. Подготовить план до написания кода

План должен содержать:

1. расшифровку выбранных решений простым языком;
2. перечень `ready`, `blocked` и `deferred` функций;
3. открытые продуктовые вопросы;
4. изменения данных, RPC, RLS, интерфейса и публичного API;
5. обратную совместимость для существующих турниров;
6. порядок этапов и критерии готовности каждого этапа;
7. необходимые проверки;
8. явное указание, что в текущий объём не входит.

AI не должен оценивать сроки до аудита затрагиваемых RPC, таблиц и миграционной цепочки.

## 4. Расшифровка приложенного примера

В примере выбрано 17 изменений, отложено 12.

### Регистрация — выбрано полностью

Выбраны:

- максимальная вместимость;
- публичная заполненность;
- дедлайн;
- бесплатное участие или отображаемый взнос;
- состояние полного набора;
- лист ожидания.

Принятые решения:

- `capacity_rule: "approved"` — вместимость занимают только одобренные участники. Pending-заявки не уменьшают количество свободных мест;
- `count_display: "total"` — публично показывается одно суммарное занятое количество без разбивки на подтверждённых и ожидающих;
- `fee_unit: "configurable"` — организатор выбирает единицу взноса для турнира: игрок, пара или команда.

Совместное поведение `registration.fullState` и `registration.waitlist` нужно сформулировать в плане. Рекомендуемая трактовка: при полном наборе обычная регистрация закрывается, а форма меняется на действие «Встать в лист ожидания». Если пользователь хочет другое поведение, это следует уточнить до реализации этапа A+.

Правило `approved` допускает больше pending-заявок, чем мест. Это следствие выбранной модели, его нельзя «исправить» скрытым резервированием места.

### Расписание — ручной контур без автогенерации

Выбраны:

- ручное назначение и перенос;
- корты и параллельные матчи;
- проверка конфликтов;
- черновик и публикация расписания;
- минимальный отдых игрока;
- сохранение закреплённых матчей при пересчёте.

Принято `time_model: "hybrid"`: матч может иметь фиксированное время, ограничение «не ранее» или место в очереди корта.

`schedule.auto` и `schedule.duration` отложены. Следовательно, AI не должен строить автоматический генератор расписания или добавлять ожидаемую длительность матча в текущий объём.

Имеется блокирующее противоречие:

- выбран `schedule.pinned`;
- его зависимость `schedule.auto` отложена.

Правильная обработка: пометить `schedule.pinned` как `blocked_by_dependency` и не реализовывать его в ручном Scheduler. Нельзя автоматически добавить `schedule.auto`. Если под «закреплением» пользователь имел в виду сохранение опубликованных ручных назначений, это должно быть оформлено как новое уточнённое решение пользователя.

Минимальный отдых остаётся полезным без автогенерации: он участвует в предупреждениях при ручном назначении и переносе.

### Доступ — роли и три режима видимости

Выбраны:

- роль «Только результаты»;
- понятное управление помощниками;
- режимы видимости;
- передача владения;
- пароль на публичную страницу.

Принятые решения:

- `score_scope: "live_and_final"` — роль может вести LIVE и сохранять итоговый результат, но не управлять настройками турнира;
- `modes: "all_three"` — нужны публичный режим, доступ по ссылке и закрытый режим.

Передача владения и пароль имеют исходный приоритет `later`, но выбраны пользователем. Их следует планировать отдельным этапом D+ после основной модели ролей и видимости.

Пароль нельзя проверять только во Vue-клиенте или хранить открытым текстом. AI должен предложить серверную модель проверки, исключить пароль и его производные из публичного sync-state и описать срок действия полученного доступа.

### Что явно не входит

В текущий выбор не входят:

- автоматическое составление расписания;
- ожидаемая длительность матча;
- лимит матчей в день;
- отдельная пауза между раундами;
- календарь многодневных лиг;
- недельные окна и исключённые даты;
- доступность отдельных игроков;
- автоматическое назначение судей;
- отправка результатов участниками;
- ввод результатов назначенными судьями;
- каталог турниров и поисковая видимость;
- отдельные права видимости для каждой публичной вкладки.

## 5. Рекомендуемая последовательность реализации

Последовательность применяется только после явного разрешения пользователя.

### Этап 0. Аудит и фиксация контракта

- Проверить текущую схему турниров, заявок, матчей и ролей.
- Сопоставить каждый выбранный `id` с текущими экранами и RPC.
- Разрешить конфликт `schedule.pinned` ↔ `schedule.auto`.
- Зафиксировать точные состояния регистрации и расписания.
- Разбить работу на небольшие выпуски. Не объединять регистрацию, Scheduler и доступ в одну миграцию или один большой PR.

Результат: технический план с файлами, моделью данных, контрактами RPC, критериями приёмки и рисками.

### Этап A. Условия регистрации

Основной выпуск:

- поля вместимости, дедлайна, режима взноса, суммы, валюты и единицы;
- настройки организатора;
- публичный блок условий;
- серверная проверка дедлайна;
- атомарная проверка вместимости при одобрении заявки;
- понятные состояния «Регистрация закрыта» и «Мест нет»;
- обратная совместимость: `NULL`-ограничения сохраняют текущее поведение старых турниров.

Отдельный подэтап A+:

- состояния и порядок листа ожидания;
- перевод заявки между waitlist, pending, approved и rejected;
- освобождение места и продвижение следующей заявки;
- защита от одновременного одобрения на последнее место.

Для денег хранить сумму в минимальных единицах валюты или использовать другую явно обоснованную точную модель. Не добавлять платёжный провайдер: выбран только показ взноса.

Критерии готовности:

- лимит нельзя обойти прямым вызовом RPC;
- одновременное одобрение не превышает лимит;
- дедлайн одинаково трактуется клиентом и БД;
- публичный пользователь не получает закрытые контактные или служебные данные;
- корректно учитываются одиночки, пары, команды и случайное формирование пар;
- RU / EN / LT содержат все новые тексты.

### Этап B. Ручное расписание

- модель кортов и их доступности;
- поля назначения матча для трёх режимов hybrid-модели;
- действия назначения и переноса;
- серверная проверка занятости корта и игрока;
- предупреждение о нарушении минимального отдыха;
- отдельное состояние черновика и публикации;
- публичная страница показывает только опубликованное расписание;
- начатые и завершённые матчи защищены от недопустимого переноса.

Ручное назначение меняет время и корт матча, но не жеребьёвку и не участников матча. Проверка конфликтов на клиенте полезна для UX, но сервер остаётся источником истины.

`schedule.pinned` не включать, пока пользователь не разрешит зависимость или не уточнит другое значение пункта.

### Этап D. Роли и видимость

- сопоставить выбранную роль с существующими `owner`, `editor`, `counter`;
- решить после аудита, безопаснее ли расширить `counter` или добавить новую роль;
- обеспечить одинаковые права в UI, RPC, RLS и Realtime;
- роль результатов получает LIVE и финальный счёт, но не настройки, заявки, жеребьёвку или управление доступом;
- реализовать публичный режим, режим по ссылке и закрытый режим с ясной семантикой;
- проверить, что «по ссылке» не называется приватным режимом.

Подэтап D+:

- атомарная передача единственного владельца с подтверждением и журналируемым результатом;
- серверная парольная защита закрытой публичной страницы;
- очистка или отзыв сессий доступа после смены пароля.

### Этап выпуска каждого блока

Для каждого этапа:

1. добавить новую миграцию, не редактируя выпущенный baseline;
2. обновить канонический `supabase/schema.sql` и manifest миграций по правилам `docs/RELEASE.md`;
3. обновить RPC/RLS до frontend-кода, который от них зависит;
4. добавить осмысленные SQL-проверки прав, гонок и обратной совместимости;
5. обновить Vue-интерфейс и переводы;
6. выполнить fresh и upgrade тесты, сборку и связанные проверки;
7. проверить публичный и административный сценарии на мобильном размере;
8. выпустить один завершённый этап до начала следующего.

Нельзя применять `schema.sql` повторно к рабочей БД, запускать reset на связанном проекте или изменять production без отдельного разрешения пользователя.

## 6. Формат ответа другой нейросети перед реализацией

До разрешения на код AI должен вернуть ответ в таком порядке:

1. **Понятый объём** — краткая расшифровка выбранных функций и решений.
2. **Конфликты** — dependency warnings и дополнительные найденные противоречия.
3. **Что не входит** — список отложенных функций.
4. **Этапы** — небольшие вертикальные выпуски с пользовательским результатом каждого.
5. **Техническое влияние** — БД, RPC, RLS, frontend, переводы, тесты и миграции.
6. **Критерии приёмки** — проверяемое поведение и крайние случаи.
7. **Вопросы** — только решения, которые действительно блокируют первый этап.
8. **Статус разрешения** — явная фраза, что реализация ещё не начата при `implementation_authorized: false`.

Не нужно пересказывать каждое поле JSON и не нужно спрашивать повторно о решениях, уже сохранённых в `decisions`.

## 7. Готовый промпт для передачи другой нейросети

Передайте нейросети JSON и следующий текст:

```text
Ты работаешь с проектом Bracketa — Vue 3 + Supabase приложением для теннисных, падел и футбольных турниров.

Приложенный JSON имеет document_type = bracketa_feature_selection. Это продуктовый выбор пользователя, а не готовая техническая спецификация.

Сначала:
1. Проверь schema_version, согласованность selected_changes и selected_change_ids, пересечения с deferred_change_ids и все зависимости.
2. Считай selected_changes единственным текущим объёмом. Не добавляй функции из deferred_change_ids.
3. Считай значения decisions принятыми решениями пользователя. Не спрашивай их повторно.
4. Пометь выбранные функции с отсутствующими зависимостями как blocked_by_dependency. Не включай отсутствующую зависимость автоматически.
5. Изучи текущий код, Supabase-схему, RPC, RLS, миграции и тесты до выбора технической реализации.
6. Подготовь этапный технический план: пользовательский результат, модель данных, RPC/RLS, frontend, миграции, обратная совместимость, проверки и критерии приёмки.
7. Явно перечисли функции вне текущего объёма.

Если implementation_authorized = false и в моём текущем сообщении нет явной команды реализовать, не изменяй код. Верни план и только действительно блокирующие вопросы.

Соблюдай правила docs/RELEASE.md: не переигрывай baseline, не применяй schema.sql как upgrade, создавай новую миграцию, поддерживай fresh и upgrade проверки. Сервер должен обеспечивать лимиты, дедлайн, права и конфликты; блокировка кнопки во frontend недостаточна.

Обрати особое внимание на dependency_warnings. Не молча меняй выбор пользователя для их устранения.
```

После согласования плана пользователь может дать отдельную ограниченную команду:

```text
Утверждаю технический план. Реализуй только этап A — условия регистрации. Не начинай Scheduler и доступ. Заверши миграцию, RPC/RLS, интерфейс, переводы и проверки этапа A.
```

Такой формат не даёт AI превратить весь roadmap в один рискованный выпуск и сохраняет контроль пользователя над началом каждого этапа.
