## 2. Основной вывод

Регистрация с лимитом, дедлайном и понятным взносом — самостоятельное полезное улучшение, которое не зависит от Scheduler.

Scheduler стоит разделить на простое назначение времени и кортов, а затем автоматическое составление расписания. Полный набор ограничений Score7 имеет смысл для лиг, но перегружает настройку короткого турнира.

В доступе у нас уже есть основа. Сначала стоит уточнить обязанности ролей и сделать управление ими понятным; отдельные права на каждую публичную вкладку пока не нужны.

## 3. Регистрация

### Что уже есть у нас

- Публичная форма без входа в аккаунт.
- Заявки с последующим одобрением организатором.
- Отдельное отображение одобренных участников и количества заявок на рассмотрении.
- Открытие и закрытие регистрации через статус турнира.
- Одиночные участники, готовые пары и набор для случайного формирования пар.

В просмотренных формах нет настройки вместимости, дедлайна и взноса.

### Предлагаемый состав

| Возможность | Польза | Предлагаемое поведение |
|---|---|---|
| Лимит участников | Ограничивает набор под формат и ресурсы турнира | Число или «Без ограничения» |
| Публичная заполненность | Игрок понимает, остались ли места | Переключатель отображения; пример: «Занято 20 из 32 мест» |
| Дедлайн | Организатор заранее завершает набор | Необязательные дата и время с часовым поясом; прекращение приёма новых заявок по наступлении срока |
| Публичный дедлайн | Игрок понимает, когда нужно успеть | Показывать рядом с формой, по умолчанию при установленном сроке |
| Бесплатно / платно | Условия участия понятны до отправки заявки | Бесплатно либо сумма, валюта и единица взноса |
| Информация об оплате | Не создаёт ожидания оплаты на сайте | Указать, что оплата производится организатору; не добавлять оплату, счета и статусы платежей |

Пример публичного блока, значения условные:

> **Занято 20 из 32 мест**  
> Подтверждено: 18 · На рассмотрении: 2  
> Регистрация до 25 сентября, 18:00 · Europe/Vilnius  
> **Взнос: 20 € за игрока**  
> Оплата организатору. Онлайн-оплата недоступна.

### Решения, которые нужно выбрать до реализации

**Что занимает место.** Возможны два подхода:

| Подход | Преимущество | Недостаток |
|---|---|---|
| Заявка резервирует место до решения организатора | Прозрачный порядок и отсутствие набора сверх вместимости | Необработанные заявки могут занять все места |
| Место занимает только одобренный участник | Организатор свободнее выбирает состав | Заявок может оказаться больше, чем мест; это нужно явно объяснять |

Предварительная рекомендация для простого набора — резервировать место при подаче. Отмена или отказ освобождают его. Если организаторы отбирают участников по уровню, второй вариант может подходить лучше. Не стоит вводить оба режима в первую версию без подтверждённой потребности.

**Единица вместимости.** Для одиночного турнира — игроки, для готовых пар — пары, для командного — команды. При случайном формировании пар нужно считать фактически заявленных людей: одна заявка сейчас может содержать одного или двух игроков.

**Единица взноса.** Надпись «20 €» недостаточна: нужно «за игрока», «за пару» или «за команду». Для первой версии проще иметь одну понятную единицу в рамках турнира.

**Полный набор и дедлайн.** Предлагается прекращать публичный приём при первом наступившем ограничении. Срок не мешает организатору рассматривать уже полученные заявки. Ручное добавление после закрытия и возможность превышения лимита — отдельные правила, которые нужно согласовать.

**Изменение условий.** При снижении лимита ниже уже занятого количества нельзя молча удалять участников. При изменении цены или других условий во время заполнения формы игрок должен увидеть обновление до отправки.

### Что проверить при реализации

- Одновременная отправка двух заявок на последнее место.
- Отказ, отмена и освобождение места.
- Наступление дедлайна при уже открытой форме; единый часовой пояс.
- Корректный подсчёт одиночек, пар и людей при случайном формировании пар.
- Ограничения проверяются сервером, а не только заблокированной кнопкой.
- Причина закрытия и условия участия остаются видны после завершения набора.
- Старые турниры сохраняют прежнее поведение при незаданных ограничениях.
- Подписи и состояния доступны на RU / EN / LT.

Лист ожидания — полезное дальнейшее расширение, но не обязательная часть первого выпуска.

## 4. Scheduler

### Оценка возможностей Score7

| Возможность в сохранённой форме | Для короткого клубного турнира | Решение для нашего плана |
|---|---|---|
| Дата старта | Базовая необходимость | В первую версию расписания |
| Дата окончания и равномерное распределение до неё | Скорее для длинного соревнования | Отложить; отдельно учитывать часы работы кортов |
| Часовой пояс | Нужен для корректного времени | Значение по умолчанию, возможность изменить |
| Корты | Основа параллельных матчей | В первую версию |
| Ожидаемая длительность матча | Основа расчёта занятости | Для автоматического расписания |
| Минимальный отдых участника | Предотвращает слишком плотный график | Для автоматического расписания |
| Ручной режим | Нужен при задержках и переносах | До сложной автоматизации |
| Максимум матчей за день | Полезное ограничение нагрузки | Дополнительные настройки следующим этапом |
| Пауза между раундами | Нужна не каждому формату | Позже, если отдыха участников недостаточно |
| Недельные окна по дням | Уместны в лигах | Отложить до сценария лиги |
| Исключённые даты | Уместны для длинного календаря | Отложить; перерывы внутри игрового дня рассматривать отдельно |
| Доступность каждого игрока | Полезна в лиге, требует много ввода | Отложить для коротких турниров |
| Судьи и их автоназначение | Зависит от организации соревнования | После появления турниров с отдельным судейским составом |
| Перезапись назначенных дат | Нужна при пересчёте, может уничтожить ручные решения | Предпросмотр изменений и закрепление матчей |

«Отложить» здесь означает низкий приоритет для исходного сценария, а не бесполезность функции вообще.

### Какой интерфейс предлагается нам

Первичная настройка: дата → часы доступности кортов → список кортов → длительность встречи → минимальный отдых → составить расписание.

Результат: список или таблица матчей по кортам, время либо порядок выхода, ручное редактирование. Перенос должен быть удобен и на телефоне: перетаскивание может дополнять обычное действие «Перенести», но не заменять его.

Обязательные понятные состояния:

- Матч ещё не назначен.
- Игрок или корт занят.
- Не хватает времени для отдыха.
- Часть матчей не помещается в заданные часы.
- Время ориентировочное либо «не ранее».

Для тенниса очередь выхода на корт может быть полезнее обещания точного старта каждого матча. Желательно сначала обеспечить ручную корректировку очереди и времени. Автоматический массовый сдвиг по фактическому окончанию LIVE-матча — отдельное дальнейшее улучшение.

### Что нельзя потерять в реализации

- Расписание назначает время и корт уже существующим матчам; это отдельная операция от жеребьёвки соперников.
- Учитываются зависимости раундов, в том числе когда победитель предыдущего матча ещё неизвестен.
- Ручной перенос проверяется на конфликты так же, как автоматическое назначение.
- Пересчёт сохраняет закреплённые назначения; начатые и завершённые матчи не перемещаются автоматически.
- При невозможности разместить всё система объясняет причину, а не выдаёт внешне успешный неполный результат.
- Публикация расписания — явное действие после просмотра, чтобы промежуточные правки не вводили игроков в заблуждение.

Официальные страницы Score7 расходятся в описании ручных проверок: маркетинговая страница говорит о предупреждениях о конфликтах, а инструкция по переносу предупреждает об отсутствии проверки интервалов. Нельзя считать эту часть проверенным ориентиром без теста в работающем сервисе.

## 5. Доступ

### Что уже есть у нас

В настройках турнира можно добавить пользователя по email, назначить роль и удалить доступ. Есть роли `owner`, `editor`, `counter` и настройка публичности турнира.

По текущим frontend-правилам `counter` ведёт LIVE в поддерживаемых видах спорта. Внесение или исправление итогового результата доступно организаторам — это не полноценная роль «Только результаты».

### Оценка меню Score7

| Возможность | Рекомендация | Причина |
|---|---|---|
| Полное управление / только результаты | Высокий приоритет | Помощнику не всегда нужны настройки турнира и участники |
| Отзыв доступа | Сохранить и сделать понятным | Организатор должен видеть, кому и что разрешено |
| Ввод результатов судьями | Развивать вместе с ролью для результатов | Сначала достаточно ограниченного доступа к турниру; назначения на отдельные матчи — позже |
| Ввод результатов участниками | Следующий этап; выше приоритет для лиг | Сокращает ручную работу организатора |
| Передача владения | Дополнительные настройки | Полезная, но редкая операция; отличается от добавления ещё одного владельца |
| Видимость в поиске | После появления каталога | Поиск и право просмотра — разные настройки |
| Пароль на турнир | По подтверждённым запросам | Уместен для закрытых мероприятий |
| Видимость Overview / Participants / Matches отдельно | Отложить | Много комбинаций с неочевидным эффектом для посетителя |

Предлагаемая структура: «Кто управляет» и «Кто видит». Для первой версии достаточно разделов внутри настроек; отдельная вкладка оправдана, когда возможностей станет больше.

Режим «По ссылке» не означает приватность: получатель может переслать ссылку. Скрытие из каталога или поиска также не является запретом просмотра. Названия режимов должны соответствовать реальному поведению.

Самостоятельный ввод результатов — отдельный рабочий процесс, а не просто переключатель доступа. У Score7 участники отправляют результаты по персональным ссылкам, совпадение двух отчётов подтверждает счёт, расхождение передаётся организатору. Если выбирать эту функцию, нужно отдельно спроектировать подтверждение, споры, исправления и момент продвижения по сетке. Для нашего первого варианта достаточно подтверждения соперником либо организатором, без сложных таймеров автоматического принятия.

## 6. Предлагаемый порядок работ после выбора функций

Каждый этап выбирается отдельно. Следующий этап не считается автоматически разрешённым.

| Этап | Состав | Результат | Относительный объём |
|---|---|---|---|
| A. Условия регистрации | Вместимость, дедлайн, отображение взноса, публичные состояния | Игрок видит условия, организатор контролирует набор | Средний: интерфейс небольшой, важны серверные правила и конкурирующие заявки |
| B. Ручное расписание | Корты, дата/время или порядок матчей, конфликты, публикация | Организатор ведёт реальное расписание турнира | Средний–высокий: новый рабочий сценарий |
| C. Автоматическое расписание | Часы кортов, длительность, отдых, зависимости матчей, предпросмотр | Система предлагает расписание, которое можно поправить | Высокий: ограничения и пересчёт |
| D. Удобный доступ | Пояснения ролей, роль для итоговых результатов, понятная видимость | Помощник работает в пределах своей задачи | Средний: необходимо проверить реальные серверные разрешения |
| E. Самостоятельные результаты | Отправка счёта, подтверждение, разногласия | Меньше ручного переноса результатов организатором | Высокий: новый процесс и влияние на сетку |
| F. Лиги и расширенные ограничения | Недельные окна, исключения, доступность игроков, судьи | Планирование длительных соревнований | Высокий, зависит от выбранных ограничений |

Этап D можно выполнить раньше B/C, если помощники уже активно участвуют в турнирах. Этап A независим от планировщика. C опирается на B. Этапы E и F имеют смысл оценивать по реальным запросам организаторов.

Объём указан сравнительно, это не оценка в днях. Календарную оценку стоит делать после выбора правил и проверки затрагиваемых серверных функций.

## 7. Что выбрать по итогам разбора

1. Какие блоки берём: регистрация, ручное расписание, автоматическое расписание, доступ, самостоятельные результаты.
2. Основной сценарий: короткий турнир, лига или оба; от него зависит приоритет расширенных ограничений.
3. Для регистрации — что резервирует место, как считаем пары, что разрешено организатору после закрытия набора.
4. Для расписания — достаточно ли ориентировочного времени и очереди или требуется календарь с фиксированными слотами.
5. Для доступа — нужен ли помощнику только LIVE, итоговый результат или оба действия.

После выбора составляется конкретное техническое задание только на выбранный объём. В рамках этого разбора код приложения и структура базы данных не изменяются.
