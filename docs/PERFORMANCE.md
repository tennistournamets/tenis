# Шаг 11: поддерживаемость и мобильные измерения

Проверено локально 6 сентября 2026. Рабочая БД и внешняя публикация в этом
шаге не менялись. Мобильные проверки выполнены в эмуляции Chromium;
физический телефон, Safari/iOS и GPU Android отдельно не проверялись.

## Границы модулей

- `src/lib/tournamentRepository.js` — чтение согласованного снимка турнира,
  прав администратора и списка администраторов. Публичный reader разрешает
  slug один раз, затем читает свежий снимок по ID. RLS проверяется сервером
  при каждом чтении. Ошибки бросаются; отсутствие возвращается как `null`.
- `src/lib/tournamentProjections.js` — одинаковые индексы участников,
  сетов и LIVE, сортировка групп/раундов для обеих страниц. Исходные массивы
  не мутируются; групповые матчи индексируются за один проход.
- `src/lib/tournamentSync.js` — очередь, объединение событий и подписка
  Realtime. `subscribeRefreshTriggers` отвечает за online/focus/visibility
  и сверку каждые 30 секунд. На публичной странице эти триггеры живут до
  ухода со страницы, включая время без доступного ID. Возврат доступа
  обнаруживается автоматически; старый канал при этом удаляется.
- `src/components/admin/TournamentSettingsForm.vue` — черновик настроек,
  ревизии, конфликты, явная перезагрузка и сохранение.
- `src/components/admin/ManualEntryForm.vue` — ручное добавление участника,
  валидация, состояние запроса, сообщения и защита несохранённого ввода.
  Ошибка сети освобождает блокировку; повторная отправка во время запроса
  запрещена. Сохранена существующая последовательность записи участника
  и его членов с компенсационным удалением при отказе второй операции.

Формы остаются смонтированными при смене вкладки/прав. Черновик не теряется
при Realtime, а кнопки учитывают текущие права и общее состояние сохранения.
Страница управления уменьшилась с 2290 до 1858 строк; дальнейшее выделение
редактора пар/сетки можно делать отдельными небольшими изменениями.

Публичная страница различает начальную ошибку сети, отсутствие доступного
турнира, существующий турнир без матчей и сбой обновления уже показанных
данных. Есть переводы RU/EN/LT и повторная загрузка. Доказанная потеря доступа
или смена slug немедленно очищает прежние данные даже при последующем сбое сети.

## Что оптимизировано

Повторный поиск ID по slug убран из обычных обновлений публичной страницы:
одно обновление выполняет **1 RPC вместо lookup + RPC**. При смене slug,
удалении или изменении доступа ID перепроверяется; отрицательный ответ
и ошибка сети не превращаются в постоянный кеш.

В сборке отключены неиспользуемые legacy API и компоненты/директивы Vue I18n
через [официальные feature flags](https://vue-i18n.intlify.dev/guide/advanced/optimization#feature-build-flags).
Компилятор сообщений и переключение всех трёх языков сохранены и проверены
в production-сборке. Изолированный эффект флагов — около 8,08 КБ JS / 2,09 КБ
gzip; новые состояния загрузки и модуль чтения добавляют часть этого объёма.

Табло и 2D-сцена по-прежнему доступны сразу. Three.js остаётся отдельной
загрузкой при открытии 3D. Предупреждение Vite о chunk >500 КБ сохраняется:
небольшое разбиение файлов само по себе не уменьшило бы передаваемый код.

## Как повторить

1. Выполнить `npm run build`, скопировать `dist` в отдельную папку до изменения
   исходников. Для сравнения после изменения сохранить вторую сборку.
2. Запустить каждый вариант отдельно:

   ```sh
   node scripts/serve-performance.mjs /absolute/path/to/before-dist 4175
   node scripts/serve-performance.mjs /absolute/path/to/after-dist 4176
   ```

   Это локальный диагностический сервер с gzip и `no-store`, не сервер
   публикации. Он кеширует файлы в памяти: после новой сборки его перезапускают.
3. Открыть адрес первого варианта в новой сессии Playwright CLI, затем из
   корня проекта выполнить:

   ```sh
   playwright-cli -s=before open http://127.0.0.1:4175
   playwright-cli -s=before run-code --filename=tests/manual/mobile-performance.playwright.js
   ```

4. После завершения повторить со вторым адресом и новой сессией. Не запускать
   SQL-тесты или другую ресурсоёмкую работу одновременно с измерениями.

Сценарий выполняет пять холодных навигаций: 390×844, CPU ×4, сеть 1,6 Мбит/с
с задержкой 150 мс, отключённый кеш. Фикстура содержит 16 участников,
15 матчей и один активный LIVE. REST перехвачен с фиксированной задержкой
150 мс; рабочие турниры не читаются и не записываются. WebSocket закрыт
тестовым перехватчиком, обновление запускается событием `online`.

Задержка обновления измерена от локального события до изменения DOM табло:
она включает debounce 150 мс, REST-фикстуру и отрисовку. Это **не замер
доставки Supabase Realtime через интернет**; реальная доставка проверялась
в шаге 8. FCP/LCP — браузерные показатели, время сетки — появление карточки
LIVE в DOM. Все времена ниже — лабораторные измерения этой машины.

Отдельный прогон включает доступную для 3G сцену с примитивами, проверяет
видимость счёта во время загрузки, закрытие сцены, резервный 2D-режим при
отсутствии WebGL и переключение RU/EN/LT. Двухсекундная выборка кадров
относится к GPU этой машины. Модель персонажей/GLB на быстром соединении
в этом замере не загружалась.

## Результаты сравнения

Chrome 152.0.7977.76, одинаковые условия; медианы пяти холодных запусков.
Последнее сравнение выполнено последовательно без параллельных SQL-тестов.

| Показатель | До | После |
| --- | ---: | ---: |
| Начальный JS, без сжатия | 568 002 Б | 562 322 Б |
| Начальный JS, gzip | 177 881 Б | 176 471 Б |
| FCP | 1512 мс | 1500 мс |
| LCP | 1836 мс | 1828 мс |
| Появление сетки | 1823 мс | 1816 мс |
| Открытие LIVE/2D | 18 мс | 16 мс |
| Запросов на повторное обновление | 2 | 1 |
| Обновление счёта после `online` | 467 мс | 316 мс |
| Готовность сцены 3D, один запуск | 1312 мс | 1310 мс |

Подтверждённое изменение — на один HTTP-запрос меньше и примерно **32%**
сокращения задержки синтетического обновления. Начальная загрузка практически
не изменилась; разницу в несколько миллисекунд нельзя считать доказанным
ускорением. Общий начальный JS уменьшился на 5680 Б, gzip — на 1410 Б.

Диапазоны пяти запусков: сетка 1815–1846 → 1806–1822 мс, открытие LIVE
17–31 → 16–30 мс, обновление 465–477 → 313–347 мс. В этих начальных загрузках
не зарегистрированы long tasks. Выборка 3D дала около 60 кадров/с в обоих
вариантах; это показатель тестовой машины, не гарантия для мобильного GPU.
Счёт оставался видимым во время загрузки 3D, без WebGL работало 2D,
закрытие удаляло canvas. Переполнения по ширине 390 px не обнаружено.

Сырые результаты: `output/playwright/step11-before-performance.json` и
`output/playwright/step11-after-performance.json`. Скриншоты 2D/3D до/после
сохранены рядом как `step11-mobile-*.png` и просмотрены вручную.
